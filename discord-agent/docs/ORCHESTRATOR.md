# 司令塔(Orchestrator)設計 v0.1

目的: Discordで大まかな依頼を1回書くだけで、司令塔がタスクに分解し、各端末のエージェントに振り、
結果を集めて検証し、**公開だけ人の承認**を挟んで完了させる。

## 1. 全体像

```
あなた ─(#command)→ 司令塔Bot ──(#tasks: タスクJSON)──→ 各ワーカーBot(端末A/B/C…)
                       │  ▲                                  │ codex exec + studio
                       │  └──────(#tasks: 結果JSON)───────────┘
                       ├─ 状態保存(state.json → 後でSQLite)
                       ├─ 検証依頼 → QAワーカー
                       └─(#approve: 承認ボタン)→ あなた → 公開
```

- **メッセージバスはDiscord自体**を使う(MVP)。ワーカーは外向き通信のみで済み、端末間のネットワーク設定が不要。
- 司令塔は常駐1台(どの端末でもよい)。ワーカーは既存の `bot.js` を拡張して使う。
- 規模が増えて遅延・レート制限が問題になったら、バスだけRedis/HTTPに差し替える(プロトコルは同じ)。

## 2. チャンネル構成

| チャンネル | 用途 | 書き込めるもの |
|---|---|---|
| `#command` | あなたが依頼を書く | あなた / 司令塔 |
| `#tasks` | 司令塔↔ワーカーの機械用メッセージ(JSON) | Bot のみ |
| `#approve` | 承認待ち(ボタン付き) | 司令塔 / あなた(押すだけ) |
| `#log` | 進捗・エラーの人間向け要約 | Bot |
| `#designer` `#coder` `#qa` | 個別に直接指示したいとき(現行の動き) | あなた |

## 3. ロール

| ロール | 担当 | 備考 |
|---|---|---|
| orchestrator | 依頼の分解、割り振り、進行管理、承認ゲート | codexは使わず、分解のみLLM呼び出し |
| designer | STUDIO上のレイアウト/見た目の編集 | STUDIOを触るのはこのロールだけにして衝突を防ぐ |
| writer | 文言・記事・SEO・画像素材 | STUDIOのCMS更新はdesignerへ依頼 or MCP次第 |
| qa | スクリーンショット確認、リンク切れ、レスポンシブ、文言チェック | プレビューURLを見る。**書き込み権限なし** |
| publisher | 公開操作 | 承認トークンがない限り動かない |

## 4. タスクプロトコル(`#tasks` のJSON)

```jsonc
// 司令塔 → ワーカー
{ "v":1, "type":"task", "id":"t-0012", "job":"j-003",
  "to":"designer", "deps":["t-0010"],
  "title":"トップのヒーローを差し替え",
  "instructions":"…具体的な作業指示…",
  "inputs":{ "previewUrl":"…", "assets":["…"] },
  "acceptance":["ヒーロー画像が新画像になっている","SPで崩れない"],
  "timeoutMin":30, "attempt":1 }

// ワーカー → 司令塔
{ "v":1, "type":"result", "id":"t-0012", "from":"designer",
  "status":"done|failed|blocked",
  "summary":"…", "artifacts":{ "previewUrl":"…", "screenshots":["…"] },
  "error":null }
```

- ワーカーは自分宛(`to`)のメッセージだけ処理し、他は無視。
- 長い成果物はDiscordの添付 or リンクで渡す(JSONには要約だけ)。
- `id` で冪等化(同じタスクを二重実行しない)。

## 5. ジョブの流れ(状態遷移)

```
received → planned → running → verifying → awaiting_approval → published
                         │         │              │
                         └─failed──┴─retry(≤2)────┴─rejected→ running(修正)
```

1. **received**: `#command` の依頼を受信、ジョブID発行。
2. **planned**: LLMで「タスク列+依存関係+受け入れ基準」に分解。**計画は `#log` に要約を出す**(初期は承認制にして精度を見る)。
3. **running**: 依存が解けたタスクから並列でワーカーへ。ワーカーは同一サイトを同時に触らない(designerは1人=直列)。
4. **verifying**: 全タスク完了後にqaへ。受け入れ基準を満たさなければ差し戻し(最大2回、超えたら人に通知)。
5. **awaiting_approval**: プレビューURL+スクショ+変更要約を `#approve` に出し、✅公開 / ❌差し戻し ボタン。
6. **published**: 承認されたら publisher が公開。完了を通知。

## 6. 完全自動化のための安全装置

- **公開ゲート**: publisher は承認トークン(ジョブID+承認者ID)がなければ拒否。最初は必須。慣れたら「低リスク変更(文言のみ等)は自動承認」を設定で許可。
- **上限**: 1ジョブのタスク数、リトライ回数、1日の実行回数、1タスクのタイムアウト。超えたら停止して通知。
- **許可ユーザー**: 依頼と承認は `ALLOWED_USER_IDS` のみ。Bot同士のメッセージも `to`/署名で検証(`#tasks` は人が書けない権限に)。
- **キルスイッチ**: `!halt` で司令塔が新規割り当てを停止し、全ワーカーに中断を送る。
- **スナップショット**: 公開前にSTUDIO側のバージョン/バックアップを確認(できる範囲で)。
- **権限最小化**: qaは読み取りのみ、publisherは公開のみ、といったロール別のCodex権限。

## 7. 状態の持ち方

- MVP: `state.json`(ジョブ・タスク・進行状況)。書き込みは司令塔だけ。
- 再起動時: `running` のタスクを `#tasks` の履歴と突き合わせて復元、未応答はタイムアウト扱いで再送。

## 8. 既存 `bot.js` の変更点(ワーカー化)

- `#tasks` を購読し、`type:"task" && to===AGENT_NAME` のJSONを処理(Bot発言を無視する現行ロジックは、`#tasks` のみ例外)。
- `codex exec` の指示文に `instructions` と `acceptance` を組み立てて渡す。
- 結果を `type:"result"` JSONで返信。人間向け要約は `#log` へ。
- 直接指示(個別チャンネル)の動作は現状のまま残す。

## 9. 実装フェーズ

| Phase | 内容 | 完了条件 |
|---|---|---|
| P0 | 現行Botで1端末・1タスクが動く | `!ping` と指示→返信が通る |
| P1 | ワーカー化(`#tasks` のJSON入出力) | 手でJSONを投げて結果が返る |
| P2 | 司令塔: 分解→割り振り→集約(計画は人が承認) | 「トップの文言を直して」で1タスクが完走 |
| P3 | qaロール+差し戻しループ | 崩れたページを検出して差し戻せる |
| P4 | `#approve` ボタン+publisher | 承認でのみ公開される |
| P5 | 計画承認の自動化、低リスク自動承認、上限・キルスイッチ整備 | 無人で1日回して事故なし |

## 11. designer のブラウザ操作方針(決定事項)

- Codex に Playwright MCP を登録し、STUDIOエディタをブラウザで操作させる(例: `codex mcp add playwright -- npx @playwright/mcp@latest --user-data-dir <専用プロファイル>`。オプション名は導入時に `--help` で確認)。
- **専用プロファイルでSTUDIOに手動ログイン済みにしておく**(ログイン情報をエージェントに渡さない)。
- designer は**1台・直列実行**に固定(同一アカウントの同時操作を避ける)。
- 各タスクの最後に必ずスクリーンショットを撮って `artifacts` に添付させる(qaの入力にもなる)。
- 画面が想定と違う・ログイン切れ・確認ダイアログ等は `status:"blocked"` で返し、推測で進めない。
- UI変更で壊れやすいので、操作手順を `docs/studio-playbook.md` に蓄積し、指示文に含める。
- MCPが使えるようになったら、designerのツールだけ差し替える(プロトコルは不変)。
